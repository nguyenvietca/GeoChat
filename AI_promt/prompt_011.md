# Goal

Implement the first version of the Notification module.

Notifications should be persisted in PostgreSQL and exposed through REST APIs.

For this milestone, notifications are generated for important user events:

1. Friend request received.
2. Friend request accepted.
3. New direct message.

The notification system should be designed so future event types can be added without rewriting the module.

This milestone is BACKEND ONLY.

# 4. Notification Type

Create a strongly typed notification type.

At minimum:

```text
FRIEND_REQUEST_RECEIVED
FRIEND_REQUEST_ACCEPTED
NEW_MESSAGE
```

Use the project's existing enum/database conventions.

Do not use arbitrary strings throughout the code.

Future notification types should be easy to add.

---

# 5. Notification Reference

Notifications should be associated with the object/event that caused them.

Example:

```text
FRIEND_REQUEST_RECEIVED
referenceType = FRIEND_REQUEST
referenceId   = requestId
```

Example:

```text
FRIEND_REQUEST_ACCEPTED
referenceType = FRIEND_REQUEST
referenceId   = requestId
```

Example:

```text
NEW_MESSAGE
referenceType = MESSAGE
referenceId   = messageId
```

This allows the client to navigate to the related resource later.

Do not store entire domain objects inside notifications.

---

# 6. Notification Content

For this milestone, notification content can be generated by the backend.

Examples:

```text
"User A sent you a friend request."

"User B accepted your friend request."

"User C sent you a new message."
```

Do not implement a complex template engine.

However, avoid hardcoding notification creation logic throughout controllers.

Centralize notification creation in the Notification service/factory layer.

---

# 7. Notification Creation Service

Provide an application/service API similar to:

```text
createFriendRequestReceived(...)
createFriendRequestAccepted(...)
createNewMessage(...)
```

or an equivalent clean design.

The important requirement is:

```text
Friend module
        ↓
Notification service

Chat module
        ↓
Notification service
```

Do not make Notification directly manipulate Friend or Chat database tables.

Avoid circular module dependencies.

---

# 8. Friend Request Notification

When:

```text
A → B
friend request
```

is successfully created:

```text
recipient = B
type = FRIEND_REQUEST_RECEIVED
reference = friend request
```

Create exactly one notification for the successful request.

IMPORTANT:

Only create the notification after the friend request has been successfully persisted.

Do not create notifications for failed requests.

---

# 9. Friend Accepted Notification

When:

```text
B accepts A's request
```

create:

```text
recipient = A
type = FRIEND_REQUEST_ACCEPTED
reference = friend request
```

Only create the notification after the accept operation succeeds.

Do not notify the user when:

- request does not exist
- request is already processed
- authorization fails

---

# 10. New Message Notification

When:

```text
A → B
message
```

is successfully persisted:

```text
recipient = B
type = NEW_MESSAGE
reference = message
```

If the conversation contains two participants:

- sender does not receive a notification for their own message
- the other participant receives the notification

Do not create a notification for the sender.

For this milestone, assume direct conversations only.

Do not implement group message notifications.

---

# 11. WebSocket Integration

PROMPT_010 already implemented realtime messaging.

Do NOT create a second message persistence path.

The flow should be:

```text
WebSocket
   ↓
Chat Service
   ↓
persist message
   ↓
create notification
   ↓
broadcast realtime chat event
```

The exact ordering may be adjusted according to transaction/event design, but notification must only be created for a successfully persisted message.

REST message sending from PROMPT_009 should also trigger the notification.

Therefore:

```text
REST send message
       ↓
Chat Service
       ↓
Notification

WebSocket send message
       ↓
Chat Service
       ↓
Notification
```

Both paths must reuse the same business logic.

---

# 12. Transaction / Event Design

Avoid tightly coupling domain modules through direct controller calls.

Prefer an application event/domain event approach if it fits the existing architecture.

For example:

```text
FriendRequestCreatedEvent
FriendRequestAcceptedEvent
MessageCreatedEvent
```

Then Notification listens to these events.

However, do NOT introduce a complicated event-driven architecture.

A simple Spring application event mechanism is sufficient if appropriate.

IMPORTANT:

Do not create a notification if the originating transaction fails.

If events are used, understand the transaction boundary and ensure notification persistence does not produce inconsistent data.

For this MVP, a synchronous transactional approach is acceptable.

# 13. Notification List API

Create:

```http
GET /api/v1/notifications
```

Return notifications belonging only to the authenticated user.

Example:

```json
{
  "items": [
    {
      "notificationId": "xxx",
      "type": "NEW_MESSAGE",
      "title": "New message",
      "message": "User B sent you a new message.",
      "referenceType": "MESSAGE",
      "referenceId": "yyy",
      "isRead": false,
      "createdAt": "..."
    }
  ]
}
```

Never return notifications belonging to another user.

---

# 14. Notification Ordering

Return newest notifications first:

```text
created_at DESC
```

Use deterministic ordering:

```text
created_at DESC
id DESC
```

or another appropriate existing convention.

---

# 15. Pagination

Notifications can grow indefinitely.

Do NOT return all notifications.

Implement pagination.

Prefer a simple:

```text
limit
offset
```

if that matches existing project conventions.

Example:

```http
GET /api/v1/notifications?limit=20&offset=0
```

Use:

```text
default limit = 20
maximum limit = 50
offset >= 0
```

unless the existing project already has a standard.

Do not create a generic pagination framework for this feature.

---

# 16. Unread Count

Create:

```http
GET /api/v1/notifications/unread-count
```

Example:

```json
{
  "count": 5
}
```

Count only notifications belonging to the authenticated user where:

```text
is_read = false
```

Perform the count in PostgreSQL.

Do not retrieve all notifications into Java and count them.

---

# 17. Mark Notification as Read

Create:

```http
POST /api/v1/notifications/{notificationId}/read
```

Rules:

- authenticated user required
- notification must belong to current user
- mark `is_read = true`
- set `read_at`
- operation should be idempotent

Calling the endpoint multiple times should not produce an error simply because the notification is already read.

Example response:

```json
{
  "notificationId": "xxx",
  "isRead": true,
  "readAt": "..."
}
```

---

# 18. Mark All as Read

Create:

```http
POST /api/v1/notifications/read-all
```

Only update notifications belonging to the authenticated user.

Example:

```text
recipient_id = currentUser
AND is_read = false
```

This operation should be idempotent.

If there are no unread notifications, return a successful response according to existing API conventions.

---

# 19. Authentication

All notification APIs require JWT authentication.

Current user must come from JWT.

Never accept:

```text
userId
recipientId
ownerId
```

from the client for determining ownership.

The server must enforce:

```text
notification.recipientId == authenticatedUserId
```

---

# 20. Security

Notification responses must not expose:

- password
- password hash
- JWT
- refresh token
- private authentication information
- unrelated private user information

Reference IDs are allowed because they are needed to navigate to the related resource.

However, authorization must still be enforced when accessing the referenced resource.

Do not assume:

```text
having notification.referenceId
```

means the user automatically has access to that resource.

---

# 21. API Error Handling

Follow existing project error conventions.

Handle:

```text
401 Unauthorized
```

for unauthenticated requests.

For:

```text
notification does not exist
notification belongs to another user
```

follow the project's existing security/not-found convention.

Do not leak information about another user's notifications.

# 34. Manual Verification

2. Register User B.
3. Login as A.
4. Send friend request to B.
5. Login as B.
6. Call:

```http
GET /api/v1/notifications
```

7. Verify B has:

```text
FRIEND_REQUEST_RECEIVED
```

8. Check unread count.

---

### Friend Accepted

1. Accept the request as B.
2. Login as A.
3. Retrieve notifications.
4. Verify A has:

```text
FRIEND_REQUEST_ACCEPTED
```

---

### New Message

1. Open A-B direct conversation.
2. Send message A → B through REST.
3. Verify B receives `NEW_MESSAGE`.
4. Send message B → A through WebSocket.
5. Verify A receives `NEW_MESSAGE`.
6. Verify sender does not receive a notification for their own message.

---

### Read

1. Mark one notification as read.
2. Verify `isRead = true`.
3. Verify `readAt` is populated.
4. Verify unread count decreases.
5. Call mark-read again.
6. Verify it remains successful.

---

### Read All

1. Create multiple unread notifications.
2. Call:

```http
POST /api/v1/notifications/read-all
```

3. Verify unread count becomes:

```text
0
```

---

### Authorization

1. Login as User C.
2. Attempt to access User A's notification.
3. Verify access is denied.
